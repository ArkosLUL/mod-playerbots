Add `raidtest.py window --jobs <file.json>`, which runs a list of jobs on one build:

- A job has `boss` (trace slug), `scenario` (DC token), `raid`, `pools` (default the raid's three), `diff` (default per raid as today), `pulls` (valid pulls wanted per pool, default 1), `cap` (most pulls per pool, default 2), `head` (commit-ish whose later builds count, default the window's `--head`) and `label` (free text such as `polish`, `confirm`, `check-10`).
- One server lock for the whole window. Unless `--skip-rebuild`, the dirty-tree check, capped rebuild and restart run once at the start, exactly as `cycle` does them. No baseline phase: a job's baseline is that pool's valid pulls of the same boss and difficulty built before its `head`, as `Ledger.baseline` reads them today.
- Scheduling: a pool runs at most one DC run at a time; job order is priority; whenever a pool is free it starts the earliest job that still wants pulls on it. `--max-raids N` (default 6) caps DC runs in flight across both raids. A job is done when each of its pools has `pulls` valid pulls after its `head` or has run `cap` pulls. Waiting on runs and matching traces (instance id plus run window) stay as they are.
- Failures: a refused start, or a DC failure that names one run, fails that job alone, and its other pools stop taking it. SOAP going down, a crash, or a failed build or restart stops the whole window; every started run is stopped or awaited before the lock is released.
- Report, markdown to stdout: a window header (build HEAD, rebuilt or not, and per job its label, boss, diff, verdict and valid/pulled per pool), then today's per-boss report for each job, then a load line over all the window's traces plus the most DC runs that were in flight at once. Load is the RaidObs snapshot gap: in each trace take the lines with `"e":"snap"`, their field `t` (ms, only `t >= 0`), and the differences of consecutive `t`; report mean, p95, p99, max and how many exceed 400 ms. The cadence is 250 ms; one, two and three parallel 25-man fights all read p95 about 320 ms and max under 450.
- Exit codes as in `cycle`: 0 every job met its pulls, 1 a cap ran out first, 2 refused before touching the server, 3 stopped on a failure.
